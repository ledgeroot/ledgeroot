## 零、生态位：链上稳定币 × agent 小额 402 支付

> 🎯 **这是全文的前提。** 下面所有关于买方、产品、取舍的判断都建立在这一节之上。

**我们做的是：agent 自主花钱时，通过 402 协议完成的小额链上稳定币支付。**

**我们不做大额。** 大额商业结算是 Shopify / Stripe / Visa TAP / Mastercard 的地盘。理由不是"打不过"，是**那个场景不需要我们**——它有发票、有合同、有退款流程、有争议解决，买方已经在用成熟工具。**进不去，也不该进。**

### 为什么这个位是结构性存在的

卡组织的费率结构把低于 1 美元的交易锁死了：**$0.30 + 2.9% 的固定成本，摊在 $0.005 的支付上等于 6000% 的手续费。** 这不是"体验不好"，是**物理上不可行**。

所以 **x402 存在的原因不是"加密更酷"，是卡组织做不了这个粒度。** 这条约束有两个方向相反的推论：

1. **传统轨道无法向下覆盖** —— Stripe / Visa 再努力，费率结构不改就进不来
2. **我们也无法向上覆盖** —— 所以不要试图做大额

**这是一个由费率结构保证的生态位，不是由技术优势保证的。** 这一点很重要：它意味着我们被保护的方式不是"别人做不到"，而是"别人做了不划算"。

> ⚠️ **2026-09-18 第七次修订：这条"不划算"只对一类玩家成立。**
>
> **Amazon Bedrock AgentCore payments 已于 2026-08-18 GA，而且它就站在这个位上**（官方用例：付费 API、MCP 工具、付费内容、pay-per-inference；上限：`maxSpendAmount` + expiry；协议：x402 v1/v2 + MPP + `upto`）。
>
> | 玩家类型 | 在 $0.005 上 | 原因 |
> |---|---|---|
> | 卡组织 / Stripe | ❌ 不可行 | 按交易金额抽成，**原论证成立** |
> | **云厂商（AWS）** | ✅ **可行，甚至亏本也做** | **按请求 / 算力 / 服务订阅计费，与支付金额解耦**；它要的是 agent workload 留在 AWS |
>
> → **护城河挡住的是"抽成型"对手，挡不住"把支付当平台功能送"的对手——而后者是最有钱、最有渠道的那一类。** §零 上面的推论（"买方是财务/AP""产品是账""零外泄是商业情报保护"）**依然成立**，但**"这个位里没有那三家最强的对手"这一节必须补上第四家**，且它是唯一一家**同时拥有分发与能力面**的。
>
> → **未被推翻的部分**：它是交易的**当事人**（持有凭据、编排支付、指示签名），**因此结构上不能同时是验证的中立方**。这正是 Ledgeroot 仍然守得住的那一格——**"记账人不能同时是审计师"**。详见 [aws-agentcore-payments-analysis.md](./aws-agentcore-payments-analysis.md) §6.3。

### 这个位里有什么、没有什么

| 有 | 没有 |
|---|---|
| agent 自主发起、机器对机器的支付 | 人类发起的采购 |
| 单价 $0.001–$0.05 | 需要发票 / PO / 合同 |
| 高频（一个 agent 群每月可达百万笔） | 单笔金额需要审批 |
| 对手方是数据 / API 服务方 | 对手方是供应商 |

⚠️ **铁轨是真实的，需求还是推测的。** 见 §七 风险 3。

### 为什么这个位里没有那三家最强的对手

| 玩家 | 瞄准的 | 为什么不在这个位 |
|---|---|---|
| **Vaara** | 欧盟 AI Act / 产品责任（高风险系统） | "高风险 + 责任翻转"是**大额、高后果**框架，美分级支付不在射程。其 SPEC 有 x402 settlement profile，但**记录别处发生的结算，不授权也不执行支付** |
| **OAP / APort** | 通用 tool call 门控（`code.push.main`、`rm -rf` 等） | 托管执行按席位收费（$499/$4,990 月费），与"每笔 $0.005"的粒度无关 |
| **Shopify / Stripe / Visa / Mastercard** | 大额商业结算 | **费率结构不容许**（见上） |

**这三家不来，不是因为他们不知道，是因为各自的经济模型把这个位排除在外。**

### 这个位改变了什么（下面三节的依据）

1. **买方变了** → 合规部门在小额场景里**暂时不在场**：FATF 与 MiCA 明确针对**有金额门槛的受监管中介**，EU AI Act 第 12 条只覆盖**高风险系统**。真正有痛点的是**财务 / AP 对账**——**没有任何 ERP 数据结构能表示"230 万笔 $0.005 的支付"**。见 §二 取舍 B。
2. **产品变了** → **不是收据，是账。** 见 §四。
3. **三根支柱的意义变了**（能力不变，理由全变）：
   - **执行前授权**：**更重要**——笔数超出人能管理的范围，必须机器强制
   - **完整性证明**：理由从"审计师要"变成"**让人相信那个聚合数字**"——230 万条里少一条，聚合就不可信
   - **零外泄**：理由从"合规"变成"**支付流量本身就是商业情报**"——你在买什么数据、向谁买、买多少、什么时候买

## 一、核心矛盾，以及它为什么是伪矛盾

本地优先架构**天然没有计量点**：

- 无计量点 → 无法按量收费
- 无流量可见性 → 无法卖数据/分析
- MIT 许可 → 无法卖软件本体
- 跑在用户机器上 → 无托管收入
- 用户自持密钥 → 无托管收入

这正是 TrustBench 把自己的战略文档写成"让出 local-first 这条道"的原因——**那条道没法变现**。

**但这个矛盾只在个人开发者市场成立。对企业客户，结论完全反过来：**

> 个人开发者不在意数据出境，所以"本地"对他是无所谓；
> **受监管企业不能把支付证据发给第三方，所以"本地"对他是唯一合规选项。**

竞争格局印证这一点：

| 玩家 | 架构 | 在"不能外发数据"的企业面前 |
|---|---|---|
| Pieverse | TEE 托管钱包 + 收据存 BNB Greenfield | ❌ 出局 |
| Coinbase | 数据流经它的轨道与 Facilitator | ❌ 出局 |
| TrustBench | 路由器，看见全部流量 | ❌ 出局 |
| Black_Wall | action payload 发到它的 API，4–8 秒 | ❌ 出局 |
| **EVIDIQ**（2026-09-17 复核新增） | 收据在 0G Storage，但 **prompt + response 全文上传到它的服务器** | ❌ 出局 |
| **Vaultra**（2026-09-17 复核新增） | 7 层合规 SDK，**决策全文上传**至其服务，$299/mo | ❌ 出局 |
| **OAP / APort**（第四次修订新增） | 默认走 `aport.io` **云端注册表与判定服务**；passport 由注册表签发 | ❌ 出局（是架构选择，非技术做不到） |
| **Vaara**（第四次修订二更正） | ⚠️ **自托管、无 SaaS、无遥测、无注册**，断网单文件可验，原文 "The evidence does not depend on the vendor" | ✅ **它通过了这一列**——但它的 grant 由**自己的 credential broker 铸造**，不是用户自签 |
| PEAC | 库，但验证需抓 issuer JWKS；无强制力 | ⚠️ 半出局 |
| **Ledgeroot** | 本地、零外泄、离线可验、有强制力、**凭据由用户 EIP-712 自签** | ⚠️ **不再是"唯一可行"**——见下 |

> ⚠️ **第四次修订二：本节的核心论证已被削弱。** 原表把"不能外发数据"当作 Ledgeroot 的独占格，理由是"对手结构上做不到"。**Vaara 做到了**（自托管 + 断网可验 + 明示不依赖厂商），于是这一列**从"独占"变成"两家通过"**。
>
> **Ledgeroot 在这一格里仅剩的差异是凭据模型**：**用户自己签**（EIP-712，私钥不出本机）vs Vaara 的 **broker 铸造**。这是真实差异，但比原来声称的窄得多。详见 [vaara-competitive-analysis.md](./vaara-competitive-analysis.md) §四。
>
> **这也意味着 §二 的取舍、§三 的分层、§四 的商业论点都建立在"独占客户群"之上——那个前提现在需要重新检验。**

> ⚠️ **第六次修订：上面的表在第六次修订后降级为"次要筛选器"。** 生态位定义已移到 §零——"不能外发数据"不再是**定义**买方的条件，而是**生态位的推论**：在小额高频场景里，支付流量本身就是商业情报，所以零外泄是自然要求，不是合规要求。
>
> 也就是说：**先有 §零 那个位，才有"不能外发数据"这个筛选器**，不是反过来。

**所以问题不是"要不要保留本地优先"，而是"目标客户是那些 agent 在替它花钱的企业"。**
把本地优先生成商业负担，是因为找错了客户——**而现在更准确的表述是：找错了生态位。**

## 二、四个取舍

### 取舍 A：变现"证据的生产"还是"证据的消费"？

**必须选消费端。**

- **生产端（引擎）必须永久免费开源** —— 它是标准的载体。收费直接杀死采用率，而采用率是唯一的护城河来源。
- **收费点只能在证据被"消费"的地方**：报告、控制台、企业部署、SLA。

### 取舍 B：卖给个人开发者还是企业？—— **卖给企业的"财务 / AP 对账"，不是"合规"**

**不能骑墙。**

个人开发者付费意愿趋近于零，而且他们要的恰恰就是免费。

建议：**免费层拿标准位置，企业层赚钱。** 中间**不要**设计"个人版 $9/月"——它是收入的幻觉，还会污染开源叙事，让企业觉得你是个玩具。

> ⚠️ **第六次修订：企业内部的哪一部门？这一条以前写错了。**
>
> 原表把买方写成"部署会花钱的 agent 的企业，及其**财务 / 合规 / 法务**团队"。**对 §零 的小额生态位，合规那一角是空的**：
>
> | 部门 | 在 $0.005 场景里 |
> |---|---|
> | **合规 / 法务** | ❌ **暂时不在场**——FATF 与 MiCA 针对**有金额门槛的受监管中介**；EU AI Act 第 12 条只覆盖**高风险系统**。Traceipt 官网说得最直白：*"they target regulated intermediaries above dollar thresholds, **not cent sized agent payments**"* |
> | **财务 / AP 对账** | ✅ **痛点在这里**——**没有任何 ERP 结构能表示"230 万笔 $0.005 的支付"**。发票、PO、月结、供应商主数据全部失效 |
> | **工程 / 平台** | ✅ 次要买方——他们要的是策略强制与 agent 不失控，愿意为"能设限额并证明它生效了"付费 |
>
> **推论**：产品的第一交付物不是"审计报告"，是"**能进 ERP 的账**"。合规报告是**后续**的扩展层（等监管真的覆盖到这个粒度时），不是入口。

### 取舍 C：为了商业化要不要碰托管 / 代币 / 平台？

三个都不要，理由各自不同：

| 不做 | 理由 |
|---|---|
| **托管** | 直接杀死支柱 3，而支柱 3 是企业**唯一**的购买理由。自毁式变现。 |
| **代币** | 杀死企业信任。Pieverse 有代币，但它服务的是消费者和 2.4 亿聊天用户，不是银行的合规部门。我们进不去那个市场，也不该进。 |
| **平台** | 我们没有分发面。Coinbase（23,000+ 资源）和 Pieverse 已在那儿。拿劣势打人家的优势。 |

### 取舍 D：锚定和签名要不要收费？

**不要。**

这两样**正在变成入场券**（半衰期 6–12 个月：Traceipt 已上线，x402 草案已写成标准，IETF 在推）。

对入场券收费 = 告诉市场"我们只有入场券"。**它们必须免费，且必须做到业界最好。**

## 三、商业模式：开源内核 + 企业控制面 + **对账与聚合层**

| 层 | 内容 | 定价 |
|---|---|---|
| **引擎**（Ledgeroot） | 策略强制 + 证据生成 + 离线验证 | **永久免费开源**（MIT） |
| **控制面**（MandateKey 的进化） | 多 agent / 多 mandate 舰队管理、组织策略库、审批流、告警、SSO、**可自托管** | 按席位 / 按 agent 订阅 |
| **对账与聚合层** ⬅️ 第六次修订 | **把百万笔微支付压成能进 ERP 的东西**：按对手方 / 按 agent / 按任务聚合、可下钻到单张收据、异常视图、对账导出 | 按份 / 年度 |
| （扩展层）合规交付物 | 证据包 → 审计师 / 税务局 / 保险方可接受的报告，带 SLA | 按份 / 年度 |

> ⚠️ **第六次修订：第三层从"合规交付物"改为"对账与聚合层"。** 理由见 §零 与 §二 取舍 B——**在小额生态位里，合规买方暂时不在场，财务/AP 才是**。合规交付物降为**扩展层**：等监管真的覆盖到这个粒度时再上，现在做它是为不存在的需求写报告。
>
> 📌 **为什么这一层不能省**：按 §零 的粒度算，**"收据"本身永远不能是产品**（$0.005 的万分之一）。能收费的只有**把收据变成账**这件事。这也是 `取舍 D`（"不做按调用收费"）的完整推论——不是"按调用收费不划算"，是"**笔这一层不存在收入，收入只能在聚合层**"。

### 关键设计：控制面只看元数据

```
┌─────────────────────────────────────────────────┐
│  控制面（付费，企业自托管或我们托管）              │
│  谁持有什么授权 · 聚合花费 · 异常告警 · 审批流     │
│  看得见：元数据                                    │
│  看不见：原始证据                                  │
└─────────────────────────────────────────────────┘
                      ▲ 仅上报元数据
                      │
┌─────────────────────────────────────────────────┐
│  数据面（免费，永远在客户机器上）                  │
│  策略强制 · 收据生成 · 哈希链 · 锚定 · 离线验证    │
│  零外泄                                            │
└─────────────────────────────────────────────────┘
```

**这样收费不违反主权** —— 因为主权本来就是卖给他们自己的。企业自己部署两个面。

> ⚠️ **第六次修订：上面这张图的"仅上报元数据"是一个未决设计，不是一个已定方案。**
>
> 生态位的产品是**跨 fleet 的聚合**（§三 对账与聚合层），而架构是**每 agent 本地一个 SQLite**。**跨 fleet 聚合需要把 N 个 agent 的数字汇到一处——而"一处"就是服务器。** 这与"零外泄"和"控制面只看元数据"存在张力。
>
> 三条候补方案的对比见 [architecture-gaps.md](./architecture-gaps.md) §C1，**推荐"每 agent 自算 rollup + 锚定链接"**——因为它同时保住零外泄与可验证性：
>
> > 每个 agent 锚定 `(receiptCount, root)`；控制面**不必看到任何收据**，就能验证"这个 agent 报的聚合数字没有漏"。**完整性证明因此不只是竞品对齐项，它是这张图能否成立的承重墙。**
>
> → 该决策登记为 [roadmap.md](./roadmap.md) **Q7**，**必须在 P1-6（对账与聚合层）之前定，否则返工。**

> 结构性优势：MandateKey 已经拆成独立仓库了。这个决定是对的，**必须坚持**——控制面要能随时 SaaS 化或自托管，而数据面不动。

## 四、产品定义：**不是收据，是账**

> ⚠️ **2026-09-17 第六次修订：本节标题从"唯一能证明没有遗漏的审计报告"改为上面这句。**
>
> 这是 §零 生态位的直接推论，也是这个产品**名字本来就在说的事**——项目叫 **Ledger**oot（账本根），不是 Receiptroot。

### 4.1 为什么"收据"不能是产品

按 §零 算一笔账：单笔 $0.005。**即使按 1% 抽成（荒谬），每笔收入是 $0.00005。** 一个 agent 群跑 230 万笔，毛收入 $115。

**所以"每笔收据"这一层在经济上不存在。** 这不是定价问题，是粒度问题——`取舍 D` 写的"不做按调用收费"说得对，但它的完整推论是：**收入只能在聚合层。**

### 4.2 那产品是什么

一个企业 agent 群一个月的真实形状：

```
230 万笔支付 · $11,400 · 47 个对手方 · 平均 $0.005 · 3 个 agent 群
```

在这组数字面前：

| 没人会做的事 | 需要有人做的事 |
|---|---|
| 逐张查看 230 万张收据 | 按对手方 / 按 agent / 按任务**聚合** |
| 用发票 / PO / 月结去表示它 | 生成**能进 ERP 的数据结构** |
| 等监管来要（他们现在不管这个粒度） | 让财务**能关账** |
| 事后审计 | **实时看异常**：谁在涨、哪条策略拦得最多 |

**产品是把左边变成右边的那一层。**

### 4.3 在这个粒度下，哪些已有能力突然变值钱

| 能力 | 在大额场景 | 在 §零 的小额场景 |
|---|---|---|
| **拒绝留痕**（拒付也出收据） | 合规价值 | ⭐ **运营价值**——230 万次尝试里被拦下的那些，直接表现为 **agent 任务失败**。这是你唯一能看见它的地方，而对手没有这个视图 |
| **完整性证明（非省略）** | 审计师要 | ⭐ **是聚合数字可信的前提**——230 万条里少一条，聚合就不可信。**理由从"合规"变成"可信度"** |
| **执行前授权（mandate）** | 风控 | ⭐ **更重要**——笔数超出人能管理的范围，必须机器强制 |
| **零外泄** | 合规要求 | ⭐ **商业情报保护**——你在买什么数据、向谁买、买多少、什么时候买 |
| **六段收据** | 证据 | **原始素材**，不是交付物 |

> 📌 **注意最后一行**：六段收据在这个生态位里是**原料**，不是产品。这个定位不影响它的工程质量——**聚合层要可信，底下的收据必须逐张可独立验证**。这反而是 `roadmap.md` N7（独立验证器）与 N10（断网单文件验证）的**商业理由**，而不只是"对标对手"。

### 4.4 一句给非技术读者的话

> **"你的 agent 这个月花了多少钱、花在哪、哪些被拦下了、每一笔怎么证明——一张能交给财务的账。"**

## 附：原有分析（第四次修订保留，供追溯）

审计师真正在意的从来不是"有没有签名"——那个 2026 年谁都有。他们在意的是：

> **你能不能证明你没有藏？**

这个问题**依然是对的**，而且依然是商业论点的正确方向。**变化在于：现在已经有公开规范回答了它，而我们不是那个规范。**

| 玩家 | 能否证明非省略 | 复核后状态 |
|---|---|---|
| x402 Receipt Attestation 草案 | ❌ 测试 3.2.4 **明确承认**"遗漏不影响单张签名有效性" | ✅ 仍成立 |
| Traceipt | ❌ 只有单张包含证明 | ✅ 仍成立 |
| TrustBench | ❌ 无锚定，更无从谈完整性 | ✅ 仍成立 |
| Black_Wall | ❌ 无 | ✅ 仍成立 |
| Pieverse | ❌ 无 | ✅ 仍成立 |
| **OAP** | ❌ 无（有 per-agent SHA-256 哈希链，但不做非省略证明） | ⚠️ **本轮新增，仍无** ← 我们未失分 |
| **Vaara Receipt** | ✅ **有，且更完整**：`seq` + 签名 `runningCount` + 封存记录 + RFC 3161 锚 + `maxClass` | ❌ **本轮新增，是唯一让我们失分的一家** |
| **Ledgeroot** | ✅ 哈希链回指 + epoch Merkle 根 ⇒ 序列无缺口 | ⚠️ 机制等价但**粒度更粗、无独立 checker、无 eIDAS 时间戳** |

### 修订后的结论

1. ❌ **"支柱 2 是唯一可以拿去卖的东西"不成立。** 它是**一回事**（auditor 要的确实是这个），但**不再是我们独有的能力**，也不再是"抄不动"的。
2. ⚠️ **但商业方向没有被否掉**——被否掉的是"我们独有"这个前提。`roadmap.md` P1-1 的优先级**不变**，只是性质从"产品化我们的独有能力"变成"**接入并达到已发布的规范标准**"。
3. ❌ ~~真正仍然抄不动的，是 §一 那个"不能外发数据"的客户群~~ → ⚠️ **第四次修订二更正：该论证已被削弱。** 原理由是"对手结构上做不到"，但 **Vaara 做到了**（自托管、无 SaaS、无遥测、断网单文件可验）。**这一格从"独占"变成"两家通过"。**
   - **仅剩的真实差异**：**凭据由用户 EIP-712 自签**（私钥不出本机）vs Vaara 的 **credential broker 铸造**；以及**支付语义为主界面**而 Vaara 是通用 tool call 门控。
   - ⚠️ **注意**：这两条是"差异"，不是"护城河"。**Vaara 有能力覆盖它们**（它承诺"No new primitives are planned"，但那是承诺不是约束）。

→ **动作改为**：按 Vaara §6.4 实现 held-set completeness + 发布公开一致性向量与独立 checker + **单文件断网验证器**（`roadmap.md` §2.4 的 **N6 / N7 / N10**），然后以"**唯一支付专用、凭据由用户自签、零出境**的合规实现"竞标——**而不是以"唯一能证明完整性"竞标**。

**支柱 2 不是一个技术特性，它是商业论点的方向——但它已经不是我们的护城河，而是一道正在被别人关上的门。**

### 买方是谁（第六次修订）

Ledgeroot 的 mandate 是**付款方侧**的授权凭证。所以：

- **付费方** = 部署"会花钱的 agent"的**企业**——**首要买方是财务 / AP**（痛点：关不了账），**次要买方是工程 / 平台**（痛点：agent 失控）。**合规 / 法务暂时不在场**（见 §二 取舍 B）
- **验证方** = 财务系统 / ERP、内部审计，以及**未来的**监管方（要求独立可验，不装我们的软件）
- **不是** 卖方（那是 ERC-8004 声誉的领域，另一个市场）

> ⚠️ **第六次修订更正**：原写"及其财务/合规/法务团队（有真实预算）"。**对 §零 的小额生态位，合规与法务没有预算动机**——他们关心的是高风险系统与合规门槛，而 $0.005 的支付不触发任何一条。**不要对着这个部门做产品。**

## 五、现在就该做的五条"留缝"

> 这些**同时服务于免费层的质量**，所以是纯收益，没有"过早商业化"的代价。

1. **证据包格式做成可移植、可第三方独立验证**
   → 这是"卖对账层"的前置条件。**财务系统 / ERP 与内部审计**必须能**不安装任何 Ledgeroot 组件**就完成验证。
   → ⚠️ 第六次修订：这一条在 §零 的生态位里**更重要**——聚合层的可信度完全依赖底层收据能独立验证。**"能独立验证"从合规要求变成了产品的可信度基础。**

2. **多 agent / 多 mandate 从第一天就支持**
   → 企业天然是多 agent 的。现在硬编码"单用户单库"，后面要重写。

3. **控制面与数据面彻底解耦**
   → MandateKey 已独立成仓库，坚持住。控制面可随时 SaaS 化或自托管，数据面不动。

4. **收据带 schema 版本号 + 自描述**
   → 审计留存是多年期的（Pieverse 提到 5 年）。格式必须能演进。

5. **独立性证明（P1-1）优先于一切花哨功能**
   → 见 §四。

## 六、现在绝不要做的

| 不做 | 理由 |
|---|---|
| **不要为了"企业感"加多租户 auth / billing** | 市场还没到，这会拖垮你。TrustBench 的创始人明确把"多租户 auth/billing"列进回避清单——**他的判断是对的** |

| **不要现在就开始卖** | 见 §八 |

## 七、诚实的风险

三条不好听的：

**1. 企业销售是另一种技能。**
架构决定了客户是银行 / 资管 / 受监管实体，而这类客户的销售周期、采购流程、安全审查，跟做开源项目完全是两回事。如果团队里没人能做这件事，"企业版"就是画在纸上的。

**2. 报告格式不是技术问题，是领域问题。**
Traceipt 做的是 VAT 合规 PDF——那需要真去问会计和税务的人。要做"审计师接受的报告"，真正的功课是**去和审计师谈**，不是写代码。这一步做不了，商业层就是空的。

**3. 市场可能太早——而且这一条在 §零 的生态位里更尖锐。**
2026 年 9 月，agent 支付还在"谁有牵引"阶段：**Vaara ≈2,164 次/周**、APort 614、BlueTier 111、TrustBench 近 30 天签发收据 **0**。而这批项目里**没有一家公布具名客户**。

> ⚠️ **第六次修订：换成 §零 的角度看，这条风险的性质变了。**
>
> 原来的担心是"企业会不会买 agent 支出审计"。**在 §零 的生态位里，真正的问题是：那个位有量吗？**
>
> - **铁轨是硬的**：卡组织费率结构决定了 x402 这个粒度必须存在（§零）
> - **量是软的**：我们掌握的"规模"数字（Coinbase 口径的 1 亿+ 笔 x402）是**他们的自报**；实测到的生态面很小（TrustBench 登记 1,592 个端点但**签发收据 0**）
> - **所以赌注是"车会来"，不是"板子搭得对"**
>
> **这条风险不能靠做产品解决，只能靠时间或靠找到那个已经在花钱的客户。** 它也是 `§八 启动信号` 里那个判据的最强形式：**如果找不到一个已经在跑百万笔级别 agent 支付的企业，商业层就不该启动。**

## 八、启动信号

**方向定了，但不要现在启动商业化动作。**

具体做法：先做掉 §五 的五条留缝（它们同时提升免费层质量），然后在 P2 阶段**用真实数据换一次判断**：

| 观察到的信号 | 判断 | 动作 |
|---|---|---|
| **有人主动问"能不能出一份我们财务能用的东西"**（第六次修订：原来是"审计能用的东西"） | 需求存在 | 启动商业层 |
| **有人已经在跑百万笔级别的 agent 支付，并抱怨关不了账** | ⭐ **生态位被验证**——这是比上一条更强的信号 | **立即启动对账层** |
| 有企业问"能不能私有部署" | 主权是真痛点 | 启动企业部署线 |
| 只有个人开发者在用，且都只要免费 | 市场未到 | 继续做标准位置，不投商业层 |
| ~~竞品开始做完整性证明~~ → **已发生**（Vaara v1.4.0） | 拐点已到 | ⚠️ 该信号**已触发**，见 [standards-landscape.md](./standards-landscape.md) §二 |
| 有对手把产品重心转向**小额 402 支付**（如 Vaara 放弃"高风险系统"叙事） | ⚠️ **生态位受威胁** —— 这是最强警报 | 重新评估整个 §零 |

**这个顺序不能反。** 先造商业层再找客户，是当前规模一定会输的打法。

## 十一、三条非直销路径

**原则：既然做不了直销，就不要设计一个需要直销的产品。**

| 路径 | 形态 | 前置条件 | 我们准备好了吗 |
|---|---|---|---|
| **PLG 自助** | 用户自己下载、自己配置、自己付费，全程无人工介入 | 产品必须**完全自助**；引擎已免费是优势 | ⚠️ 需确认控制面能否自助部署 |
| **伙伴代销** | GRC 平台 / 会计事务所 / 云市场替你卖 | 产品必须**可嵌入、可白标** | ⚠️ 需设计嵌入接口 |
| **OEM 嵌入** | 某合规厂商把 Ledgeroot 当模块买断 | **必须先是标准**，否则对方自己写 | ❌ 未开始（P3-1 收据规范） |

### 三条路径的共同前置条件

这三条**指向同一件事**，而这正是好消息——**它们不改变现在要做的事**：

1. **引擎必须是标准** → `roadmap.md` P3-1（发布收据规范）
2. **验证必须能独立跑** → `roadmap.md` P1-2（独立验证器包）
3. **格式必须自描述、可版本演进** → `roadmap.md` P0-1 的 schema 版本决策（Q1）
4. **证据包必须可移植** → `commercialization.md` §五 留缝 1

> 换言之：**`§五` 那份留缝清单一个字都不用改。** 团队结构的变化只影响未来商业层的形态，不影响当前工程优先级。

### 优先级建议

**OEM 嵌入 > 伙伴代销 > PLG 自助。**

理由：OEM 不需要销售团队（对方卖）、不需要自助产品打磨（对方做交付）、单价最高。但它**要求先成为标准**——所以它与"免费开源拿标准位"的路线完全同向，不冲突。

## 十二、如果没有商业化

**必须提前承认这个可能性，并把它视为可接受的结果。**

以当前的市场成熟度和团队结构，这个项目完全可能不走商业化路线，而其价值依然成立：

| 结果 | 含义 | 达成条件 |
|---|---|---|
| **标准位置** | 成为 x402 证据层的事实格式，被更大的玩家收编或合作 | P3-1 收据规范发布 + PEAC L3 兼容 + 生态提交 |
| **声望资产** | 在 agent 支付赛道建立技术信用，反哺团队的其他方向 | P0 正确性全部修完（**带着缺陷的代码不产生声望**） |
| **被收购标的** | 架构与标准位置被卡组织 / Coinbase / GRC 厂商吸收 | 上述两者 |

### ⚠️ 必须避免的反模式

> **为了"必须有个商业模式"而扭曲产品，比没有商业模式更糟。**

最容易犯的错，是在市场没到的时候为了显得像门生意去加：多租户、计费系统、企业功能、SSO。这会**同时**失去开源采用率和产品锐度——而这恰好是 TrustBench 创始人在其内部文档里明确列为"要回避的技能"，他的判断是对的。

**判据**：任何商业层功能，如果在没有真实企业客户的情况下开发，就不做。
