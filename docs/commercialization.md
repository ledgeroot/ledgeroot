# 商业化方向

> 定位：生态位、买方、产品定义、商业模式与启动信号
> 状态：2026-09-22
> 关联：[roadmap.md](./roadmap.md) · [architecture.md](./architecture.md) · [competitors.md](./competitors.md) · [standards.md](./standards.md) · [landscape.md](./landscape.md) · [tokenized-equities.md](./tokenized-equities.md)
> 一句话结论：**免费开源内核拿标准位置，向"agent 在花钱"的企业卖对账与授权能力；但现在不启动商业化，且商业层不得设计成需要直销的形态。** 买方从"合规"改为"**财务 / AP 对账**"，产品从"审计报告"改为"**聚合与对账**"。

---

## 零、生态位：链上稳定币 × agent 小额 402 支付

> 🎯 **这是全文的前提。** 下面关于买方、产品、取舍的判断都建立在这一节之上。

**我们做的是：agent 自主花钱时，通过 402 协议完成的小额链上稳定币支付。** **我们不做大额**——大额商业结算有发票、合同、退款、争议解决，买方已在用成熟工具（Shopify / Stripe / Visa TAP / Mastercard），进不去也不该进。

### 为什么这个位是结构性存在的

卡组织费率把低于 1 美元的交易锁死：**$0.30 + 2.9% 摊在 $0.005 上 = 6000% 手续费**。这不是"体验不好"，是**物理上不可行**。

**所以 x402 存在的原因不是"加密更酷"，是卡组织做不了这个粒度。** 两个方向相反的推论：传统轨道无法向下覆盖；我们也无法向上覆盖（所以不做大额）。

**这是一个由费率结构保证的生态位，不是由技术优势保证的。** 它意味着我们被保护的方式不是"别人做不到"，而是"别人做了不划算"。

> ⚠️ **这条论证有一个 AWS 形状的洞**：它排除的是**按交易金额抽成**的对手（卡组织 / Stripe），**不排除按负载计费、把支付当平台功能送的云厂商**。**AWS AgentCore payments 已 GA 且就站在这个位上。** 护城河挡住"抽成型"对手，挡不住"把支付当平台功能送"的对手——而后者是最有钱、最有渠道的那一类。详见 [competitors.md](./competitors.md) §二。
>
> → **未被推翻的部分**：AWS 是交易的**当事人**（持有凭据、编排支付、指示签名），**因此结构上不能同时是验证的中立方**——这正是我们仍然守得住的那一格。**"记账人不能同时是审计师"。**

### 这个位里有什么、没有什么

| 有 | 没有 |
|---|---|
| agent 自主发起、机器对机器支付 | 人类发起的采购 |
| 单价 $0.001–$0.05 | 需要发票 / PO / 合同 |
| 高频（一个 agent 群每月可达百万笔） | 单笔金额需要审批 |
| 对手方是数据 / API 服务方 | 对手方是供应商 |

⚠️ **铁轨是真实的，需求还是推测的。** 见 §七 风险 3。

### 这个位改变了什么

1. **买方变了** → 合规在小额场景**暂时不在场**（FATF / MiCA 针对有金额门槛的受监管中介，EU AI Act 第 12 条只覆盖高风险系统）。真正有痛点的是**财务 / AP 对账**——**没有任何 ERP 数据结构能表示"230 万笔 $0.005 的支付"**。见 §二 取舍 B。
2. **产品变了** → **不是收据，是账。** 见 §四。
3. **三根支柱的意义变了**（能力不变，理由全变）：**执行前授权更重要**（笔数超出人能管理的范围）；**完整性证明**理由从"审计师要"变成"让人相信那个聚合数字"；**零外泄**理由从"合规"变成"支付流量本身就是商业情报"。

## 一、核心矛盾，以及它为什么是伪矛盾

本地优先架构**天然没有计量点**：无计量点 → 无法按量收费；无流量可见性 → 无法卖数据；MIT → 无法卖软件本体；跑在用户机器上 → 无托管收入。

**但这个矛盾只在个人开发者市场成立。对企业客户，结论反过来**：

> 个人开发者不在意数据出境，所以"本地"对他无所谓；**受监管企业不能把支付证据发给第三方，所以"本地"对他是唯一合规选项。**

竞争格局印证（下表是**次要筛选器**，不再是定义买方的条件）：

| 玩家 | 架构 | 在"不能外发数据"的企业面前 |
|---|---|---|
| Pieverse | TEE 托管钱包 + 收据存 BNB Greenfield | ❌ 出局 |
| Coinbase | 数据流经它的轨道与 Facilitator | ❌ 出局 |
| TrustBench | 路由器，看见全部流量 | ❌ 出局 |
| EVIDIQ | 收据在 0G Storage，但 **prompt + response 全文上传** | ❌ 出局 |
| Vaultra | 7 层合规 SDK，**决策全文上传** | ❌ 出局 |
| OAP / APort | 默认走云端注册表与判定服务 | ❌ 出局（架构选择） |
| **Vaara** | 自托管、无 SaaS、无遥测、断网单文件可验 | ✅ **它通过了** |
| PEAC | 库，但验证需抓 issuer JWKS | ⚠️ 半出局 |
| **Ledgeroot** | 本地、零外泄、离线可验、有强制力、**凭据由用户 EIP-712 自签** | ⚠️ **不再是"唯一可行"** |

> ⚠️ **"不能外发数据"这一格从"独占"变成"两家通过"**（Vaara 做到了）。**Ledgeroot 仅剩的差异是凭据模型**：**用户自己签** vs Vaara 的 **broker 铸造**——真实差异，但比原来声称的窄得多。

**所以问题不是"要不要保留本地优先"，而是"目标客户是那些 agent 在替它花钱的企业"**——更准确地说是"**找对了生态位**"。

## 二、四个取舍

### 取舍 A：变现"证据的生产"还是"证据的消费"？—— **必须选消费端**

- **生产端（引擎）必须永久免费开源**——它是标准的载体。收费直接杀死采用率，而采用率是唯一的护城河来源。
- **收费点只能在证据被"消费"的地方**：报告、控制台、企业部署、SLA。

### 取舍 B：卖给谁？—— **卖给企业的"财务 / AP 对账"，不是"合规"**

**不能骑墙。** 个人开发者付费意愿趋近于零，且他们要的恰恰是免费。**免费层拿标准位置，企业层赚钱**；中间**不要**设计"个人版 $9/月"。

| 部门 | 在 $0.005 场景里 |
|---|---|
| **合规 / 法务** | ❌ **暂时不在场**——FATF/MiCA 针对有金额门槛的受监管中介；EU AI Act 第 12 条只覆盖高风险系统 |
| **财务 / AP 对账** | ✅ **痛点在这里**——没有任何 ERP 结构能表示"230 万笔 $0.005 的支付"。发票、PO、月结、供应商主数据全部失效 |
| **工程 / 平台** | ✅ 次要买方——要策略强制与"能设限额并证明它生效了" |

**推论**：产品的第一交付物不是"审计报告"，是"**能进 ERP 的账**"；合规报告是**后续扩展层**，不是入口。

### 取舍 C：要不要碰托管 / 代币 / 平台？—— 三个都不要

| 不做 | 理由 |
|---|---|
| **托管** | 直接杀死支柱 3，而支柱 3 是企业**唯一**的购买理由 |
| **代币** | 杀死企业信任；那是消费者市场 |
| **平台** | 我们没有分发面；Coinbase（23,000+ 资源）与 Pieverse 已在那儿 |

### 取舍 D：锚定和签名要不要收费？—— **不要**

这两样**正在变成入场券**（半衰期 6–12 个月）。对入场券收费 = 告诉市场"我们只有入场券"。**它们必须免费，且必须做到业界最好。**

## 三、商业模式：开源内核 + 企业控制面 + **对账与聚合层**

| 层 | 内容 | 定价 |
|---|---|---|
| **引擎**（Ledgeroot） | 策略强制 + 证据生成 + 离线验证 | **永久免费开源**（MIT） |
| **控制面**（MandateKey 的进化） | 多 agent / 多 mandate 舰队管理、组织策略库、审批流、告警、SSO、**可自托管** | 按席位 / 按 agent 订阅 |
| **对账与聚合层** | **把百万笔微支付压成能进 ERP 的东西**：按对手方 / agent / 任务聚合、可下钻到单张收据、异常视图、对账导出 | 按份 / 年度 |
| （扩展层）合规交付物 | 证据包 → 审计师 / 税务局 / 保险方可接受的报告，带 SLA | 按份 / 年度 |

> 📌 **为什么这一层不能省**：按 §零 的粒度算，**"收据"本身永远不能是产品**（$0.005 的万分之一）。能收费的只有**把收据变成账**。这也是取舍 D 的完整推论——不是"按调用收费不划算"，是"**笔这一层不存在收入，收入只能在聚合层**"。

### 关键设计：控制面只看元数据

```
┌─────────────────────────────────────────────────┐
│  控制面（付费，企业自托管或我们托管）              │
│  谁持有什么授权 · 聚合花费 · 异常告警 · 审批流     │
│  看得见：元数据        看不见：原始证据            │
└─────────────────────────────────────────────────┘
                      ▲ 仅上报元数据
┌─────────────────────────────────────────────────┐
│  数据面（免费，永远在客户机器上）                  │
│  策略强制 · 收据生成 · 哈希链 · 锚定 · 离线验证    │
│  零外泄                                            │
└─────────────────────────────────────────────────┘
```

**这样收费不违反主权**——因为主权本来就是卖给他们自己的。

> ⚠️ **"仅上报元数据"是未决设计（Q7），不是已定方案。** 生态位的产品是跨 fleet 聚合，而架构是每 agent 本地一个 SQLite——**跨 fleet 聚合需要把 N 个 agent 的数字汇到一处，而"一处"就是服务器**。三条候补方案的对比见 [architecture.md](./architecture.md) §三，**推荐"每 agent 自算 rollup + 锚定链接"**——它同时保住零外泄与可验证性。
>
> → **完整性证明因此不只是竞品对齐项，它是这张图能否成立的承重墙。** 见 `roadmap.md` **Q7**，**必须在 P1-6 之前定。**

> 结构性优势：MandateKey 已拆成独立仓库——**坚持它**。控制面要能随时 SaaS 化或自托管，而数据面不动。

## 四、产品定义：**不是收据，是账**

项目叫 **Ledger**oot（账本根），不是 Receiptroot。

### 4.1 为什么"收据"不能是产品

按 §零 算一笔账：单笔 $0.005，**即使按 1% 抽成（荒谬），每笔收入 $0.00005**。一个 agent 群跑 230 万笔，毛收入 $115。**"每笔收据"这一层在经济上不存在**——这不是定价问题，是粒度问题。

### 4.2 那产品是什么

```
230 万笔支付 · $11,400 · 47 个对手方 · 平均 $0.005 · 3 个 agent 群
```

| 没人会做的事 | 需要有人做的事 |
|---|---|
| 逐张查看 230 万张收据 | 按对手方 / agent / 任务**聚合** |
| 用发票 / PO / 月结去表示它 | 生成**能进 ERP 的数据结构** |
| 等监管来要（他们现在不管这个粒度） | 让财务**能关账** |
| 事后审计 | **实时看异常**：谁在涨、哪条策略拦得最多 |

**产品是把左边变成右边的那一层。**

### 4.3 在这个粒度下，哪些已有能力突然变值钱

| 能力 | 在大额场景 | 在 §零 的小额场景 |
|---|---|---|
| **拒绝留痕** | 合规价值 | ⭐ **运营价值**——被拦下的那些直接表现为 **agent 任务失败**，这是唯一能看见它的地方 |
| **完整性证明** | 审计师要 | ⭐ **聚合数字可信的前提**——230 万条里少一条，聚合就不可信 |
| **执行前授权** | 风控 | ⭐ **更重要**——笔数超出人能管理的范围 |
| **零外泄** | 合规要求 | ⭐ **商业情报保护**——你在买什么数据、向谁买、买多少、什么时候买 |
| **六段收据** | 证据 | **原始素材**，不是交付物 |

### 4.4 一句给非技术读者的话

> **"你的 agent 这个月花了多少钱、花在哪、哪些被拦下了、每一笔怎么证明——一张能交给财务的账。"**

## 五、现在就该做的五条"留缝"

> 这些**同时服务于免费层的质量**，所以是纯收益，没有"过早商业化"的代价。

1. **证据包格式做成可移植、可第三方独立验证** —— "卖对账层"的前置条件。**财务系统 / ERP 与内部审计必须能"不安装任何 Ledgeroot 组件"就完成验证。** ⭐ 在 §零 的生态位里**更重要**：聚合层的可信度完全依赖底层收据能独立验证。
2. **多 agent / 多 mandate 从第一天就支持** —— 企业天然是多 agent 的。
3. **控制面与数据面彻底解耦** —— MandateKey 已独立成仓库，坚持。
4. **收据带 schema 版本号 + 自描述** —— 审计留存是多年期的。
5. **独立验证器（P1-2）优先于一切花哨功能。**

## 六、现在绝不要做的

| 不做 | 理由 |
|---|---|
| 不要为了"企业感"加多租户 auth / billing | 市场还没到，会拖垮你 |
| 不要让验证依赖 Ledgeroot 的基础设施 | 一旦依赖，主权叙事崩，"卖报告"也失去独立性 |
| 不要做按调用收费 | 需在请求路径里，与本地优先冲突 |
| 不要现在就开始卖 | 见 §八 |

## 七、诚实的风险

**1. 企业销售是另一种技能。** 架构决定了客户是受监管实体，这类客户的销售周期、采购流程、安全审查跟做开源项目完全是两回事。**没有能做这件事的人，"企业版"就是画在纸上的。**

**2. 报告格式不是技术问题，是领域问题。** 要做"审计师/财务接受的报告"，真正的功课是**去和审计师、AP 谈**，不是写代码。这一步做不了，商业层就是空的。

**3. 市场可能太早——而且在 §零 的生态位里更尖锐。** 2026 年 9 月，agent 支付还在"谁有牵引"阶段：Vaara ≈2,164/周、APort 614、BlueTier 111，而这批项目里**没有一家公布具名客户**。

> **在 §零 的角度看，真正的问题是：那个位有量吗？** 铁轨是硬的（费率结构决定这个粒度必须存在）；量是软的（"规模"数字是自报，实测生态面很小）。**赌注是"车会来"，不是"板子搭得对"。** **判据**：如果找不到一个已经在跑百万笔级别 agent 支付的企业，商业层就不该启动。

## 八、启动信号

**方向定了，但不要现在启动商业化动作。** 先做掉 §五 的五条留缝，然后在 P2 阶段**用真实数据换一次判断**：

| 观察到的信号 | 判断 | 动作 |
|---|---|---|
| 有人主动问"能不能出一份我们财务能用的东西" | 需求存在 | 启动商业层 |
| **有人已在跑百万笔级 agent 支付，并抱怨关不了账** | ⭐ **生态位被验证**（比上一条更强） | **立即启动对账层** |
| 有企业问"能不能私有部署" | 主权是真痛点 | 启动企业部署线 |
| 只有个人开发者在用，且都只要免费 | 市场未到 | 继续做标准位置，不投商业层 |
| 有对手把产品重心转向**小额 402 支付** | ⚠️ **生态位受威胁——最强警报** | 重新评估整个 §零 |

**这个顺序不能反。先造商业层再找客户，是当前规模一定会输的打法。**

> **监控触发条件**（含 AWS、PEAC、卡组织、Vaara、OAP 等）统一在 [landscape.md](./landscape.md) §八。

## 十一、三条非直销路径

**原则：既然做不了直销，就不要设计一个需要直销的产品。**

| 路径 | 形态 | 前置条件 |
|---|---|---|
| **PLG 自助** | 用户自己下载、配置、付费，全程无人工 | 产品必须**完全自助** |
| **伙伴代销** | GRC 平台 / 会计事务所 / 云市场替你卖 | 产品必须**可嵌入、可白标** |
| **OEM 嵌入** | 某合规厂商把 Ledgeroot 当模块买断 | **必须先是标准**，否则对方自己写 |

**三条路径指向同一件事**（**不改变现在要做的事**）：引擎必须是标准（P3-1）→ 验证必须能独立跑（P1-2）→ 格式必须自描述可演进（Q1）→ 证据包必须可移植（§五 留缝 1）。

**优先级：OEM 嵌入 > 伙伴代销 > PLG 自助。** 理由：OEM 不需要销售团队、不需要自助产品打磨、单价最高，但它**要求先成为标准**——与"免费开源拿标准位"完全同向。

## 十二、如果没有商业化

**必须提前承认这个可能性，并把它视为可接受的结果。**

| 结果 | 含义 | 达成条件 |
|---|---|---|
| **标准位置** | 成为 x402 证据层的事实格式，被更大的玩家收编或合作 | P3-1 收据规范发布 + PEAC L3 兼容 + 生态提交 |
| **声望资产** | 在 agent 支付赛道建立技术信用 | P0 正确性全部修完（**带缺陷的代码不产生声望**） |
| **被收购标的** | 架构与标准位置被卡组织 / Coinbase / GRC 厂商吸收 | 上述两者 |

### ⚠️ 必须避免的反模式

> **为了"必须有个商业模式"而扭曲产品，比没有商业模式更糟。**

最容易犯的错是在市场没到的时候为了显得像门生意去加：多租户、计费系统、企业功能、SSO——这会**同时**失去开源采用率与产品锐度。**判据**：任何商业层功能，如果在没有真实企业客户的情况下开发，就不做。
